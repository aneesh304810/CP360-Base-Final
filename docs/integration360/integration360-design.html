Integration360

A read-only observability layer over every integration between BBH and the SEI Wealth Platform. It answers one question, for one business date, across four channels: did everything integrate correctly?

The scope in one line

Integration360 observes. It never moves data, never remediates, never writes to a pipeline table. The CP Integration Hub owns quarantine, error handling and retry; Integration360 shows what the Hub is holding and why.

The three questions

Every screen answers one of three questions, for a given channel and business date. This is the organising spine of the whole design — if a view doesn't answer one of them, it doesn't belong.

Completeness

Did everything that should have arrived, arrive — and everything that should have gone, go? Measured against an expectation, not against yesterday.

Timeliness

Did it happen inside the window? Requires knowing what was due, which today no channel records. See Assumptions.

Correctness

Do the counts reconcile at every boundary, and what is held in exception? Reconciliation is derived here, not read.

What it does and does not do

In scopeOut of scope — and who owns it
Show state of every channel per business dateMoving or transforming data — Airflow + dbt
Show exceptions: what failed, why, with what codeResolving, waiving, retrying an exception — Integration Hub

Correlate across Oracle, Airflow, the Hub and the inboxAnything inside SEI beyond what SEI publishes

Why it owns almost nothing

Integration360's own schema is five tables, and none of them hold integration state. Everything it shows is read from the system that owns it. That is what makes the observability-only claim structural rather than aspirational — there is no table in this design that another system would need to read back.

Specified — enough information to build Assumed — built on a stated assumption Blocked — needs an answer first Not owned — read or shared

Every component carries one of these states. Four are blocked — the Hub’s Foundation framework resolved three of the seven, by giving Integration360 a threshold store, an expectation store and an estate-wide error model to read.

The consequence of excluding Splunk

The pipeline publishes its own SLA and reconciliation verdicts to Splunk. Integration360 derives its own from Oracle. Two independent computations of the same judgement will drift unless both read the same threshold — which is why every verdict this system stores also stores the threshold that was in force when it was computed.

Why the inbox is shared rather than owned

If SEI pushed to Integration360 and the Hub had to obtain the content from it, an observability tool would sit on the critical path for remediation. Placing the inbox behind the Apigee proxy and in front of both consumers keeps one endpoint for SEI while letting Integration360 restart, redeploy and fail over without anyone noticing.

Deployment notes

Network zone

Integration360 runs in BBH infrastructure. It is reachable by BBH operations only; the SEI push terminates at the Apigee proxy and the inbox, never at this application.

Database access

A dedicated read-only account per source. Airflow is read from a replica — an analytical query against the scheduler's primary will degrade scheduling.

Landing zone

The cross-channel check parses a standby file's trailer. That requires a read mount, or an upstream component publishing the count. A deployment decision, not a detail.

Airflow schema coupling

The metadata schema is not a public API and changes between versions. All Airflow queries sit behind one adapter so an upgrade is a single-file change.

status_normalizer
specified

Maps each source's own vocabulary onto one canonical set, keeping the native value verbatim alongside it. Mapping is configuration, never code.

Rule
An unknown native value populates status_reason and raises an alert. It is never silently mapped to the nearest neighbour.
Rule
Terminal status never regresses. A late callback cannot move a completed submission backwards.
status_precedence
specifiedtwo writers, one status

The outbound status field has two writers — the pushed notification and the backstop poll. This resolves them by a written rule rather than by arrival order.

Rule
The poll wins. A poll is a read of SEI's current state; a notification is a point-in-time event that can arrive late, out of order, or twice.
Derivation
History keeps every row from both sources with its SOURCE. The current status is the latest POLL at or after the newest CALLBACK, otherwise the highest terminal state reached. Terminal never regresses.
Why it matters
Without the rule, a retried PROCESSING notification landing after a COMPLETED poll walks the status backwards and raises a false exception. Two writers into one field with no precedence is how a status board loses its audience.
redactor
assumed

Masks account numbers and other business keys on the way out, against a configurable field allow-list. Applied on read rather than at rest, so a wrong mask can be corrected without having destroyed the original.

Open
786 PII fields are in SDC scope and the masking policy is unapproved. Default to hashing business keys until it is signed off.

Compares what was due against what happened. Without it Integration360 reports presence and absence but never lateness — and lateness is what operations actually needs.

Blocked on
No channel has an expectation model. Inbound feeds have no calendar, the 24-loader catalogue has no cadence column, and events have no expectation definable without a marker schedule.
Recommendation

cross_channel_reconciler
assumedthe flagship check

Under standby, both paths deliver the same data every day. This compares three numbers that must agree: the file trailer's declared count, the events received for that domain and date, and the count declared by the marker.

Why it matters
A missing file is obvious. A stream that quietly dropped three percent of ACCOUNT events is not. Nothing else in the estate can detect it.
Assumption
That the marker carries a declared count. If it does not, the check degrades to two numbers and loses its strongest leg.
Also depends on
Which side is authoritative when they disagree — that decides whether a mismatch is an event defect or a file defect.
gap_detector
specifiedfinds what nothing else sees

Four checks that have no owner anywhere else in the estate:

  • Sequence gaps — Event Hub sequence numbers are monotonic per partition, so a gap is a lost event. This is a real completeness check, stronger than anything the file channel has.
  • Marker never arrived — data received, no boundary signal. Indistinguishable from "still arriving" without an expected time.
  • Stale in-progress — a registry row at LOADING older than the timeout is a stuck load; no row at all is a late file. The gate cannot tell these apart; this can.
  • Callback never returned — a submission with no status after its window. Silence looks exactly like success.
divergence_detector
specifiedwhere push and poll disagree

Three findings that exist only because the outbound channel has two status sources:

  • Silent notification — a terminal state found by the poller that no push ever announced. This is a direct measurement of whether SEI's push channel is healthy, and it costs nothing once SOURCE is recorded.
  • Contradiction — a notification the next poll disagrees with. Resolved by status_precedence, but recorded, because a pattern of them is a contract problem rather than a data problem.
  • Unresolved — a submission still non-terminal past its max age, which becomes STATUS_UNRESOLVED rather than sitting at SUBMITTED for ever.

It is the outbound counterpart of the event channel's sequence-gap check: both turn an absence into a provable one.

cadence_baseline

Two kinds of data quality, kept apart

Row-level business DQ

DQ_VALIDATION_FAILURE. This account has an unmapped status code. Grain: one failing record.

Model-level structural DQ

dbt test results. Uniqueness, not-null, referential integrity, one open row per natural key. Grain: one assertion over a model.

An operator wants both on one screen. Merging them into one list makes both harder to read — so they are presented together and classified separately, the same discipline as keeping native status beside normalised status.

Detail

Four channels

The channels are at very different maturities, and the design reflects that rather than pretending they are symmetrical.

ChannelDirectionStatusWhat Integration360 can answer
EventSEI → BBHprimary ingestion Micro-batch completeness, consumer lag per partition, sequence gaps, marker coverage, pull-complete gating. Cannot say what changed — the envelope carries no data and the pull re-reads current state.
FileSEI → BBHdaily standby Arrival and readiness of the fallback, plus the trailer count for the cross-channel check. Answers "is the parachute packed", not "did the data arrive".
LoaderBBH → SEIpush + poll Submission lifecycle, accepted and rejected counts, reject detail, the template version in force, and whether each status arrived by push or by poll. Still depends on the Hub recording the send.
APIbothnot Day 1 Nothing yet. Day 1 is file and event based; no API traffic exists to observe. Its first production member is the loader callback endpoint itself.

The taxonomy is two dimensions, not one

FILE, API and EVENT are transports. LOADER is a business flow — and it travels over the API transport. Treating channel as a single top-level partition forces every loader record to misrepresent one of them.

There is a third dimension too. Some events carry data; markers, file-ready signals and the 51 technical events carry control. That axis decides whether an event is something to ingest or something to display, so it belongs in the model rather than in a comment.

Transport

FILE · API · EVENT — how the bytes moved.

Flow

Inbound feed · loader submission · status callback — what the message is for.

Plane

Data or control — whether it is ingested or merely observed.

Cost of getting it wrong

One column now. A migration across every observation record later.

The marker is not the gate

A marker means SEI finished publishing. It says nothing about BBH finishing consuming. The gate opens on pull complete — markers received, every micro-batch loaded, every batch reconciled. Gating on the marker alone would look like a control and be a comfort.

Detail

Observation model

All intraday and EOD data now arrives as SDC events and moves through one pipeline to Stage 1, Stage 2 and Gold. Monitoring it needs two clocks, not one.

Two clocks

Intraday is continuous. There is no "complete" — only flowing at an acceptable rate, or falling behind. Health is lag, boxing continuity and Stage 1 load success over a rolling window.

EOD is a gate. Completeness is binary: EOD marker received, every micro-batch for the date LOADED, transformation run, reconciliation clean, DATE_CONTROL at COMPLETE.

On one clock the screen is either permanently amber, because intraday is never finished, or blind to an EOD running two hours late.

Timeliness without an expectation table

For the event channel, lateness is derivable from the stream’s own rhythm. Micro-batch IDs are sequential and arrive at a characteristic interval, so a rolling baseline per topic turns "MB 1049 has not arrived" into "MB 1049 is 40 minutes overdue against a 6-minute norm". That is cadence_baseline, and it needs nothing from SEI.

EOD is the exception. There is one marker a day and no rhythm to baseline against, so its expected arrival time still has to be stated — the one place the expectation model is unavoidable on this channel.

The failure mode this architecture creates

Intraday micro-batches load into Stage 1 all day while DATE_CONTROL sits at PENDING, and the transformation runs once at EOD over whatever accumulated. So a micro-batch that failed at 11am and went unnoticed means the EOD transformation runs on incomplete Stage 1 — and the reconciliation boundaries will not necessarily catch it, because STG→INT ties perfectly against a Stage 1 that is itself short.

Two consequences. Intraday needs its own alerting rather than only feeding the EOD gate. And the gate must require every micro-batch for the date to be LOADED, not merely that the EOD marker arrived.

What this cannot show

The event carries no data and the pull re-reads current state, so multiple intraday changes to one key collapse into one observation. Integration360 can say a key was touched in micro-batch 1047 and again in 1051; it cannot say what changed, and cannot reconstruct the intermediate state.

Lineage runs Gold row → micro-batch → key, never Gold row → the specific change that caused it. Worth stating plainly, because "near-real-time event streaming" sets an expectation of change-level traceability this pattern deliberately does not provide.

One model change this requires

The micro-batch now has two levels, because MB Start and End are written to every partition of every domain topic. A partition-level record holds the boxing; a parent record holds the logical batch and is what the gate aggregates against. The existing registry keyed on (topic, partition, mb_id) is the partition level — the parent is missing and needs adding.

API surface and the error taxonomy

Twenty-two operations. Twenty-one are reads; the twenty-second is the endpoint SEI calls. The full contract is integration360-openapi.yaml.

Error taxonomy — three classes, three owners

The axis that decides who is woken up, and whether a retry is legitimate at all. Without it the exception list is one undifferentiated pile that nobody owns.

ClassOwnerWhat it meansRetry
BUSINESSOperations and the sourceThe data is wrong — a missing mandatory attribute, a code outside its domain, an unresolved reference, a control total that does not tie.Never. Retrying produces the same rejection and spends the attempt budget.
TECHNICALEngineeringThe pipeline is wrong — a transformation failed, a model test failed, a schema mismatch, an unparseable envelope.Only after a fix. An unchanged retry is an unchanged failure.
SYSTEMPlatformThe platform is wrong — a timeout, a lost connection, a pod eviction, a broker rebalance, a rate limit.The only class where blind retry is legitimate, and the only one with a circuit breaker behind it.
Why the class matters more than the count

A day that is ninety percent SYSTEM is a platform incident. A day that is ninety percent BUSINESS is a source data problem. The same total means opposite things. /errors/summary exists to make that shape visible in one call, and top_codes[].delta_vs_baseline_pct is there because a code that normally fires twice and fired two hundred times is the signal — the absolute count is not.

Rules that hold across every path

Read-only, one exception

Every path is a GET except POST /sei/notifications, and that write lands in an inbox the Hub owns. Integration360 is a second consumer and is never on the remediation path.

Redaction on read

Business keys are masked on the way out, not at rest, so a wrong mask can be corrected without having destroyed the original. Unmasking needs int360.pii.read.

Cursor paging only

No offsets. The underlying tables grow while a caller pages, and an offset silently skips rows when they do.

UNKNOWN is never GOOD

When an input is unavailable the verdict is UNKNOWN. A missing Airflow replica returns 503 for that path rather than a green estate board.

Thresholds travel with verdicts

Every verdict carries threshold_in_force or tolerance_in_force, so it stays reproducible after the threshold moves and cannot silently diverge from Splunk.

Native codes survive

SEI's code is kept verbatim beside the normalised one. An unmapped value raises rather than being mapped to its nearest neighbour.

The one write, in detail

  1. Acknowledge on durable write. Authenticate, validate the envelope shape, store the raw body plus receipt metadata, return 202. Parsing, correlation and status derivation all happen downstream. A 500 because a lookup failed would tie SEI's retry behaviour to BBH's internal bugs.
  2. Generic by design. message_type is an open string and payload is unconstrained, so a new status or counter needs no contract change. An unrecognised type is stored and alerted, never rejected.
  3. Deduplication keys on message_id, which must be stable across SEI's own retries. An HTTP callback has no equivalent of the event side's (topic, partition, offset). Without it, a retried "50 records rejected" becomes 100 in the exception count.
  4. Thin. A status transition and an error summary travel here. Reject detail does not — it is fetched on the poll leg, paginated and stored.
  5. 409 is idempotent. A duplicate message_id returns the original receipt and writes nothing twice.
Detail

Runtime flows

Three sequences carry most of the design's behaviour. Everything else is a read.

1 · The outbound loader loop — submit, notify, poll

Three legs, all owned by the Integration Hub. Push notifies; poll fetches detail and backstops a notification that never arrives. The important property is that Integration360 is nowhere in the acknowledgement path and never calls SEI. It can be down, mid-deploy or failing over and neither SEI nor the Hub notices.

Leg 1 — BBH submits

  1. The Hub generates the loader file to SEI's template and submits it through the Apigee proxy.
  2. The submission identifier returned here is the correlation key every later leg hangs off. The Hub must record the submission at send time — without that row, a submission that never reached SEI is indistinguishable from one that succeeded.

Leg 2 — SEI notifies (push)

  1. SEI Workflows posts a status transition and an error summary to the BBH Apigee proxy (node 12). Thin and event-shaped — reject detail does not travel here.
  2. The proxy authenticates, enforces rate limits, and passes it on. It rejects only for authentication or a malformed envelope — never for a business reason.
  3. The message is written to the notification inbox, encrypted at rest, and acknowledged with 202. Acknowledge on durable write, not on successful processing — parsing, correlation and status derivation all happen downstream of that write. A 500 because a correlation lookup failed ties SEI's retry behaviour to BBH's internal bugs.
  4. Dedupe keys on a SEI-supplied message identifier stable across retries. Anything unparseable becomes a dead-letter row with an alert; nothing is dropped.
  5. The Integration Hub consumes the inbox to remediate, tracking its own progress marker. Integration360 consumes it independently to display, tracking a separate marker. Neither consumer blocks the other.

Leg 3 — BBH polls (backstop and detail)

  1. The Hub's monitoring worker selects non-terminal submissions only. A submission that reached a terminal state by either source drops out of the poll set, so call volume tracks work in flight rather than history.
  2. Cadence is tiered: tight for the first interval after submission, backing off after. A loader SEI processes in four minutes is not polled every five minutes until midnight.
  3. On reaching a terminal-with-errors state, reject detail is fetched once, paginated, and stored. Fetching errors on every poll would pull the same rejected records repeatedly.
  4. A submission still non-terminal past its max age becomes STATUS_UNRESOLVED — the outbound equivalent of a business date that never reaches COMPLETE.
When the two sources disagree, the poll wins

A poll is a read of SEI's current state; a notification is a point-in-time event that can arrive late, out of order, or twice. History keeps every row from both with its SOURCE; the current status is derived by status_precedence, and terminal never regresses.

The pairing also closes the hole a pure push model leaves. Under push alone, a submission whose notification never arrives sits at SUBMITTED and the failure is invisible unless something holds an expectation of it. The poller makes that a detected condition — and the gap between the two sources becomes the running measure of the push channel's own health.

2 · Nightly verdict computation

Verdicts are computed once, stored with their inputs, and read back — rather than recomputed on every page load and never kept.

  1. The Observation Engine reads the closed business date from DATE_CONTROL.
  2. expectation_evaluator establishes what was due for that date, per channel. blocked — no expectation model exists
  3. verdict_computer derives SLA state against the cutoff, and reconciliation verdicts from the boundary counts, applying the tolerance read from shared configuration.
  4. Each verdict is written to int360_verdict_snapshot with the threshold that was in force, so it can be reproduced and defended later.
  5. rollup_builder writes the daily aggregate, including cross-source correlations that no SQL join could produce.
  6. alert_evaluator compares findings against int360_alert_log and dispatches only what is new.

3 · Cross-channel reconciliation

The check that only exists because both paths deliver the same data every day. It costs two lines of a file.

  1. landing_trailer_reader parses the header and trailer of the standby file for an interface and date. The file is never loaded.
  2. The declared trailer count is compared against the events received for the matching domain and date, and against the count declared by the marker.
  3. Three numbers that must agree. Any difference is written as a reconciliation row with all three legs visible.
  4. A difference means opposite things depending on which side is authoritative — an event defect or a file defect. blocked — authority unresolved
Why this is the flagship

A missing file is obvious. A stream that quietly dropped three percent of ACCOUNT events is not, and no other control in the estate would catch it. Under the standby arrangement the second dataset is already arriving; this check is nearly free, and it is the only independent proof that the primary ingestion path is complete.

It also has a shelf life. If standby file generation sunsets once events stabilise, this capability goes with it — so it should not be the spine of the product unless standby is permanent.
